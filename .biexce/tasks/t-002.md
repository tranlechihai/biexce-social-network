# t-002 — Implement friendship requests, unfriend, and blocking policy

## 1. Objective

Deliver a consistent social graph in which authenticated users can send, inspect, accept, or reject friend requests, list and remove bidirectional friendships, and block/unblock another user with immediate bilateral relationship and interaction protection.

## 2. Context tối thiểu

- Depends on the authenticated user, database conventions, error envelope, and test fixtures established by `t-001`.
- Scope authority: `TING_TING_MVP_SCOPE.md` section 4.2 and applicable sections 5–6; master-plan criteria `TT-SOCIAL`, `TT-BLOCK`, `TT-API-QUALITY`, and `TT-TEST`.
- A friend request has observable `pending`, `accepted`, or `rejected` state. Accepting creates bidirectional friendship. At most one active pending request exists for an unordered pair; existing friendship, reverse pending request, self-request, and blocked pair are not valid new requests.
- Blocking is initiated by one user but denies viewing/interaction in both directions. It removes any friendship and pending request relationship for the pair. Unblocking does not recreate either. Closed request history may be retained, but API behavior and database constraints must remain unambiguous.
- Build a reusable friendship/block authorization policy for posts and interactions in later tasks. Expected areas are social models/repositories/services/routes plus focused unit and API integration tests; shared model/schema changes are allowed where necessary.
- Expose enough API state for the later profile/browser screen: create/list incoming or outgoing requests, accept/reject, list friends, unfriend, block/unblock, and current pair relationship.

## 3. Acceptance criteria

- [ ] **AC1 (`TT-SOCIAL`, automated integration):** Given two unrelated, unblocked users, when one sends a request, then exactly one pending request is persisted and relevant request-list/relationship responses identify sender, recipient, and state without sensitive profile data.
- [ ] **AC2 (`TT-SOCIAL`, automated unit/integration):** Given self-targeting, an existing pending request in either direction, or an existing friendship, when a request is sent, then the mutation is rejected consistently and no additional request or friendship row is created.
- [ ] **AC3 (`TT-SOCIAL`, automated integration):** Given a pending request, when its recipient accepts it, then its state is accepted and both users observe one mutual friendship; replay or an unauthorized third-party accept cannot duplicate or alter the relationship.
- [ ] **AC4 (`TT-SOCIAL`, automated integration):** Given a pending request, when its recipient rejects it, then it becomes rejected without friendship; the sender or a third party cannot accept/reject it. Given current friends, when either unfriends, then mutual friendship visibility is removed and replay does not create an error-induced duplicate state.
- [ ] **AC5 (`TT-BLOCK`, automated integration):** Given any friendship and/or pending relationship between two users, when either user blocks the other, then friendship and pending relationship are removed and neither user can create a request or observe the other as a friend while the block exists.
- [ ] **AC6 (`TT-BLOCK`, automated integration):** Given a blocked pair, when the blocker unblocks, then no friendship/request is restored; a new request is possible only through the normal request flow. A non-blocker cannot remove someone else's block.
- [ ] **AC7 (`TT-API-QUALITY`, automated integration):** Anonymous calls are unauthenticated; unauthorized state transitions are denied; unknown user/request/block resources return the chosen consistent missing-resource behavior; repeated important mutations preserve database uniqueness.
- [ ] **AC8 (`TT-TEST`, automated test):** Unit tests cover pair canonicalization and relationship/block transition rules, and integration tests cover AC1–AC7 using isolated databases.

Verify: **planned and unexecuted at plan time; use the canonical command established by `t-001`:** `.venv/bin/python -m pytest tests/unit tests/integration -k 'friend or request or block or unfriend'`.
