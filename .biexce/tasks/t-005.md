# t-005 — Deliver responsive browser flows, representative seed data, and run documentation

## 1. Objective

Deliver a responsive browser demo through which a user can complete every mandatory MVP flow without manual API calls, plus guarded transactional representative seed data, demo-account guidance, an initial browser smoke checklist, and accurate setup/seed/server/test instructions.

## 2. Context tối thiểu

- All required backend capabilities and shared authorization rules exist after `t-004`. The web layer must reuse those services/API contracts rather than duplicate or bypass them.
- Scope authority: `TING_TING_MVP_SCOPE.md` sections 4.5, 4.6, and applicable sections 5–6; master-plan criteria `TT-WEB`, `TT-SEED-DOC`, plus browser coverage of `TT-AUTH` through `TT-COMMENT`.
- Use Jinja2 and vanilla HTML/CSS/JavaScript only. Supply registration/login/logout, feed/create/edit-delete owned post controls as needed for complete post flow, own profile update, user/profile relationship controls, requests accept/reject, friends/unfriend, block/unblock, like/unlike, and comment create/delete.
- Authentication uses the HttpOnly cookie configured in `t-001`; validation/auth failures must be visibly and accessibly rendered. Responsive acceptance targets a practical narrow mobile viewport and desktop viewport, without requiring a design system or pixel-perfect styling.
- Seed only a fresh, empty, compatible SQLite target with at least three users, a friendship, representative `ONLY_ME` and `FRIENDS` posts, a like, and a comment. Preflight schema and emptiness before any write; refuse incompatible or pre-populated targets without mutation. Perform all seed writes/domain transitions in one transaction so any later failure rolls back the complete operation. Signing secret and demo password come from environment/invocation.
- Update `README.md` with actual environment/install/configuration, create-only initialization, guarded seed, server, and full/focused test commands. For seed refusal/failure, document only the non-mutating guarantee, how to correct configuration, and how to select the intended fresh empty database; do not document database lifecycle operations. Create a browser smoke checklist that `t-006` can execute and finalize.
- Expected areas include web routes/templates/static assets, web integration tests, seed module/CLI and tests, README, and a smoke-checklist document in the project's normal docs/test area. Keep pages small and module boundaries aligned with the master plan.

## 3. Acceptance criteria

- [ ] **AC1 (`TT-WEB`/`TT-AUTH`, automated web test + manual checklist):** Given a clean browser, when a user registers or logs in by username/email, then they reach an authenticated page via HttpOnly cookie; logout removes browser access; invalid input/credentials show a clear actionable message without exposing secrets.
- [ ] **AC2 (`TT-WEB`/`TT-PROFILE`/`TT-SOCIAL`, automated web test + manual checklist):** Given authenticated users, when they view/update their own basic profile and exercise request send/list/accept/reject, friends/unfriend, block/unblock controls, then visible state matches API persistence and unauthorized/invalid actions show a clear error.
- [ ] **AC3 (`TT-WEB`/`TT-POST`/`TT-FEED`, automated web test + manual checklist):** Given an authenticated user, when they create an `ONLY_ME` or `FRIENDS` text post and browse feed pages, then authorized posts appear newest-first, owned post actions are available, and invisible posts never render.
- [ ] **AC4 (`TT-WEB`/`TT-LIKE`/`TT-COMMENT`, automated web test + manual checklist):** Given a visible post, when a user likes/unlikes or creates/deletes a permitted comment, then the page reflects persisted state/counts; forbidden or validation failures are visibly reported.
- [ ] **AC5 (`TT-WEB`, screenshot/manual evidence):** Given the browser smoke checklist's desktop and narrow-mobile viewport sizes, when all mandatory pages and forms are used, then content remains readable, controls remain reachable without horizontal page overflow, labels/errors are understandable, and keyboard form submission/focus is usable.
- [ ] **AC6 (`TT-SEED-DOC`, automated integration/command output):** Given a fresh empty compatible database and an invocation-supplied demo password, when seed runs, then at least three usable users plus friendship, both post audiences, like, and comment are committed exactly as documented.
- [ ] **AC7 (`TT-SEED-DOC`, automated preflight evidence):** Given an incompatible schema or any pre-populated target, when seed is invoked, then it exits before writes with an actionable non-secret error and every pre-existing logical record remains field-for-field unchanged.
- [ ] **AC8 (`TT-SEED-DOC`, automated transaction evidence):** Given a fresh empty compatible target and an injected failure after seed writes begin, when seed runs, then the transaction rolls back and no user, friendship, post, like, or comment from that attempted seed remains.
- [ ] **AC9 (`TT-SEED-DOC`, documentation walkthrough):** Given a new local checkout with Python 3, when a reviewer follows README commands in order, then they can create an environment, install dependencies, configure a non-committed signing secret/demo password, perform create-only initialization, seed the intended fresh empty database, start the server, identify demo accounts, and invoke tests; refusal/failure guidance is limited to the no-mutation guarantee and correcting configuration/target selection.
- [ ] **AC10 (`TT-API-QUALITY`/`TT-TEST`, automated test + artifact review):** Web handlers preserve server-side authorization and consistent errors, no password/token/signing secret is rendered or logged, web integration tests cover AC1–AC4, and a stepwise browser smoke checklist covers every mandatory flow for `t-006` without claiming it has already passed.

Verify: **planned and unexecuted at plan time; use actual commands established by implementation:** `.venv/bin/python -m ting_ting.seed && .venv/bin/python -m pytest tests/integration -k 'web or seed'`. Test fresh success, incompatible/pre-populated preflight refusal, and injected-failure rollback against isolated temporary databases, then perform the browser checklist draft; record results rather than claiming planning-time PASS.
