# t-004 — Implement replay-safe likes and authorized comments

## 1. Objective

Deliver like/unlike and comment create/list/delete capabilities whose authorization follows current post visibility, whose deletion roles match scope, and whose returned counts and state agree with persisted data under retries.

## 2. Context tối thiểu

- Use authenticated identity (`t-001`), block/friend policy (`t-002`), and post read authorization (`t-003`) rather than recreating interaction-specific visibility rules.
- Scope authority: `TING_TING_MVP_SCOPE.md` section 4.4 and applicable sections 5–6; master-plan criteria `TT-LIKE`, `TT-COMMENT`, `TT-BLOCK`, `TT-API-QUALITY`, and `TT-TEST`.
- Like and unlike are idempotent: repeated identical requests have the same successful end state, with at most one like per user/post. A user lacking current read access cannot like, unlike, create/list comments, or otherwise infer interaction data.
- Comments are text-only. The comment author or the parent post author can delete a comment; all others are denied. Validate comment text and parent existence/visibility.
- Counts and current-user liked state in interaction/post responses must match committed rows after create/delete/replay. Use database uniqueness and transactional changes rather than trusting client counters.
- Expected areas are interaction models/schemas/services/routes, extension of post response summaries, and focused unit/integration tests.

## 3. Acceptance criteria

- [ ] **AC1 (`TT-LIKE`, automated integration):** Given a visible post, when an authorized user likes it once or repeatedly, then each request reaches the same successful liked state, exactly one like row exists, and returned/stored count and current-user state are correct.
- [ ] **AC2 (`TT-LIKE`, automated integration):** Given a visible post in liked or unliked state, when the user unlikes it once or repeatedly, then each request reaches the same successful unliked state, no user/post like row remains, and the count never becomes inconsistent or negative.
- [ ] **AC3 (`TT-COMMENT`, automated integration):** Given a visible post and valid bounded non-empty text, when an authorized user comments, then one comment with author/text/timestamp is stored and returned and the post's comment count increases exactly once; invalid text creates nothing.
- [ ] **AC4 (`TT-COMMENT`, automated integration):** Given comments on a visible post, when listed, then only authorized readers receive them in documented stable order. Anonymous, non-friend, and either side of a blocked pair cannot list or create interactions and receive the consistent non-leaking error behavior.
- [ ] **AC5 (`TT-COMMENT`, automated role matrix):** Given a comment, when deleted by its comment author or parent-post author, then it is removed and count decreases exactly once; deletion by any other user is denied with no data change; missing comment/post follows the error contract.
- [ ] **AC6 (`TT-BLOCK`, automated integration):** Given existing likes/comments and a later unfriend or block, when the former friend attempts any interaction or direct interaction read, then access is denied immediately. Existing records do not themselves grant visibility; unblock alone remains insufficient.
- [ ] **AC7 (`TT-API-QUALITY`, automated persistence check):** Given mixed like/comment mutations and retries, when public post/interaction responses and database rows are compared after commit, then like/comment counts and liked state agree and unrelated records are unchanged.
- [ ] **AC8 (`TT-TEST`, automated test):** Unit tests cover deletion-role and visibility rules, and integration tests cover AC1–AC7 plus anonymous, forbidden, and not-found cases.

Verify: **planned and unexecuted at plan time; use the canonical command established by `t-001`:** `.venv/bin/python -m pytest tests/unit tests/integration -k 'like or comment or interaction'`.
