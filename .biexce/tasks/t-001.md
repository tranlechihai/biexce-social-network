# t-001 — Establish the application foundation, authentication, and owned profiles

## 1. Objective

Deliver a locally runnable FastAPI/SQLAlchemy foundation on which a user can register with unique username and email, log in by either identifier, authenticate through bearer header or web cookie, log out of the browser session, read their profile, and update only their own basic profile, with passwords and secrets handled safely.

## 2. Context tối thiểu

- Scope authority: `TING_TING_MVP_SCOPE.md` sections 4.1, 5, and 6; confirmed choices and criterion IDs `TT-AUTH`, `TT-PROFILE`, `TT-API-QUALITY`, and `TT-TEST` are in `.biexce/MASTER_PLAN.md` sections 2, 5, and 6.
- The repository is greenfield. This task must establish the package layout, dependency manifest, configuration, SQLite session/schema initialization, FastAPI app, shared API error shape, and Pytest fixtures/entry points needed by all later tasks. Initialization is create-only: it may create a new database/missing MVP tables, but must not drop, truncate, or replace an existing database; incompatible existing schema/configuration fails before mutation with an actionable error.
- Use Python 3, FastAPI, synchronous SQLAlchemy 2 style, SQLite, Jinja2 availability, and Pytest. Expected areas include the application package's config/database/auth/profile/API modules and focused unit/integration tests; exact filenames are implementation-owned.
- Signed short-lived tokens support both `Authorization: Bearer` and an HttpOnly, SameSite web cookie. Cookie `Secure` is environment-controlled for local HTTP versus HTTPS staging. Signing secret/configuration is external to source and sensitive values are not logged.
- Registration requires both unique normalized username and unique normalized email. Login accepts either plus password. Use a maintained adaptive password-hashing library, never reversible/plain storage.
- API failures follow the master-plan error envelope with consistent validation, unauthenticated, forbidden, conflict, and not-found mappings. Do not leak password hashes or token values.
- Establish planned commands (or clearly documented equivalents) for editable test dependency installation and `python -m pytest`. Commands listed below are unexecuted planning targets until this task creates them.

## 3. Acceptance criteria

- [ ] **AC1 (`TT-AUTH`, automated integration):** Given a fresh database and valid unique username, email, and password, when registration is submitted, then the API creates one user, returns a non-sensitive representation with a create status, and persisted password material is a non-plain adaptive hash.
- [ ] **AC2 (`TT-AUTH`, automated integration):** Given an existing account, when valid credentials use either its username or email, then login returns a signed expiring bearer token and sets the configured HttpOnly/SameSite cookie; invalid credentials receive the consistent unauthenticated error without identifying which field was wrong.
- [ ] **AC3 (`TT-AUTH`, automated integration):** Given duplicate normalized username or duplicate normalized email, malformed email, missing required input, or invalid profile-length input, when the relevant mutation is submitted, then it is rejected with the documented validation/conflict status and no duplicate/partial row is stored.
- [ ] **AC4 (`TT-AUTH`, automated integration):** Given a protected endpoint, when called anonymously, with a malformed/expired token, with a valid bearer header, or with a valid auth cookie, then the anonymous and malformed/expired cases are consistently unauthenticated and each valid transport identifies the same user.
- [ ] **AC5 (`TT-AUTH`, automated integration):** Given an authenticated cookie session, when logout is requested, then the response expires/removes that cookie and a later cookie-only protected request is unauthenticated.
- [ ] **AC6 (`TT-PROFILE`, automated integration):** Given two users, when one reads and updates their own allowed basic profile fields, then changes persist and are returned; when they attempt to update the other user's profile, the server denies it and the other record remains unchanged.
- [ ] **AC7 (`TT-API-QUALITY`, automated test/config review):** Given handled validation, unauthenticated, forbidden, conflict, and missing-resource failures, when returned by the API, then each uses the one documented JSON error shape and appropriate stable status; application source/config/log capture contains no committed signing secret, plain password, emitted token, password hash, or sensitive credential log.
- [ ] **AC8 (`TT-TEST`, command output):** The task establishes isolated temporary-SQLite fixtures plus passing focused unit/integration tests for AC1–AC7 without skips or weakened assertions.
- [ ] **AC9 (`TT-SEED-DOC`, automated integration):** Given a new SQLite target, a compatible already-initialized Ting Ting target, an incompatible existing schema, or a non-SQLite/misconfigured target, when schema initialization runs, then it creates required structures only on the new target, leaves the compatible initialized target's schema and logical records unchanged, and fails before mutation in the incompatible/misconfigured cases; no path performs implicit drop, truncate, or database replacement.
